# AGENTS.md

Hermes plugin (`topoi`): a gateway platform package. The platform adapter is outbound-only, a delivery namespace for topics (cron results and framework notices land in topic-keyed sessions; continuable runs get a fresh reply-able thread id), while the package also serves the topic registry and topic-grouped session listings over REST (`dashboard/plugin_api.py`) for the desktop half and the dashboard Topics tab (`dashboard/manifest.json` + `dashboard/dist/index.js`). No inbound transport: nothing connects to this platform.

## Conventions

- Python 3.13 typing only: builtin generics (`dict`, `list`, `tuple`) and `X | None`. `typing.Any` is fine. No `Dict`, `List`, or `Optional`.
- No em dashes. Use hyphens.
- `topic` / `topics` is not a proper noun, so never title-case it as a brand word; grammar and UI conventions still apply (sentence starts, headings, UI labels).
- No hard-wrapped lines in comments, docstrings, or Markdown prose: write flowing lines (one sentence or paragraph per line) and let the renderer wrap; hard line breaks stay only where they are structural (code blocks, YAML, bullets).
- No plugin-side persistent storage beyond the binding store: `send()` logs only, content is read from sessions, and the topic registry lives in `config.yaml` under `platforms.topoi.topics` (`topic_store.py`, written through the REST surface under the core's config lock). Bindings are the one exception and live in the plugin-private SQLite store (`bindings.py`); they are high-churn and unbounded, which is exactly what config must not carry, and clients never see them (resolution is server-side). Offline runs are reconstructed from the cron run session plus the job's deliver config. Jobs delivering here need `attach_to_session: true` or `cron.mirror_delivery: true`.
- Comments and docstrings: short, why over what. Never reference files that are not committed (plans, drafts, spike scripts).
- A break you caused is not fixed until a check would have caught it: every regression fix ships a test that fails on the old code, pinned at the seam that actually flipped, rather than only at the call site you touched. Prefer contract assertions (`TopoiAdapter.edit_message is BasePlatformAdapter.edit_message`, the exact refusal set) over restatements of the new code.
- Format before marking work complete: `uvx ruff format .` and `uvx ruff check .`.
- Commit subjects carry a component scope: `type(scope): sentence`, lowercase type and scope, never a bare `fix:` or `feat:`. The scope names where the change lands, not its layer: `api` for the REST surface's behaviour in `dashboard/plugin_api.py` (its 404/409/422 rules included), `threads` for what the `/threads` listing and its rows return, `desktop` for the desktop half. Tests and docs ride the component whose behaviour they pin, so neither `tests` nor `docs` scopes a behaviour change, and a change spanning components takes the one carrying the behaviour.
- Dashboard bundle rules: `dashboard/dist/index.js` is a plain IIFE with no build step (JSX is not available; use `React.createElement` from `SDK.React`). React, hooks, DS components, `fetchJSON` and `timeAgo` all come from `window.__HERMES_PLUGIN_SDK__`; never import react or bundle a component library. The DS component prop shapes are their own: `Badge` takes `tone` (not `variant`), `Button` takes `outlined` / `ghost` / `destructive` / `size`, `ConfirmDialog` takes `open` / `title` / `description` / `confirmLabel` / `destructive` / `onConfirm` / `onCancel`, `Select` fires `onValueChange(value)` only and does NOT forward unknown props (an `aria-label` on it never reaches the DOM). `fetchJSON` throws `Error("<status>: <raw body>")`, so pull FastAPI's `detail` out for user-facing errors. Every registry mutation rebuilds whole state from what the page last loaded and PUTs it; one mutation at a time, and refetch after each write (a delete prunes bindings in the same write).
- Topic-row rules: name, id and thread count carry `ml-3` spacing; the Home and Archived badges both sit right of the thread count in the head (Home first, then Archived), each a plain DS `Badge` at `text-sm` with a 12px Lucide glyph leading its text (star before Home, package before Archived) and inline `style: { fontFamily: "inherit", letterSpacing: "normal" }` so the DS's compressed look (`font-compressed` plus wide tracking) never shows - inline styles beat the classes; `text-sm` also drops the DS's `text-display` uppercase through the host's twMerge-based `cn`, so the badges read in normal case; the glyphs are dynamic `import()`s of the official lucide package from the esm.sh CDN (`https://esm.sh/lucide@0.577.0/dist/esm/icons/<name>.js`, version matching the host, `ICON_URLS` + `loadIconNode` + `Icon` in the bundle) because the plugin SDK exposes no icon surface - its `components` map is DS primitives only; the vanilla `lucide` package exports dependency-free icon nodes, so no second React copy is pulled in, and a failed import leaves the spot without its glyph (no fallback); exactly one of Archive or Delete shows, chosen by thread count (threads exist -> Archive/Unarchive, none -> Delete), and both are destructive-colored. The actions are the same CDN-imported lucide glyphs in the order up, down, rename, home, archive/delete - `arrow-up`, `arrow-down`, `pencil`, `house`, `archive` / `archive-restore` / `trash-2` - with `check` and `x` while editing - each carrying an `aria-label` + `title`; lucide 0.577.0 renamed `home` to `house` (the old name 404s on the CDN, which would silently drop the glyph) and the trash icon is `trash-2`. Note the unarchive path is unreachable in practice: an archived topic's threads drop out of `GET /threads` (live topics only), so an archived row always counts 0 threads and offers delete instead of unarchive. The Recent Threads card's heading total counts only threads filed under a live topic (summed from the groups, never the store-wide API total), lists only those threads (nothing untagged, nothing orphaned), and caps each topic group at `RECENT_PER_TOPIC` (4); the group header keeps the full count. The bundle has no bind/move/unbind surface and neither does the desktop half (only the New thread flow files a chat, through `POST /threads/bind`); the API has no `/threads/unbind` route. `GET /threads` lists only threads filed under a live topic, and `DELETE /threads/{session_id}` deletes one thread for the desktop half's row action.
- Topic ids and deletion: the create row is name first, then the id field; the id is set by the user at creation (required, no auto-mint) and the field opens on a locked `t_` prefix the user cannot remove (the suffix is the user's part), shape-guarded client-side with the server as backstop, and never editable afterwards. Only a topic with no threads can be deleted; a topic with threads is archived instead. That invariant is why the registry carries no tombstone list: a `deleted` key is ignored on read, ignored (not refused) in a client-sent state, and dropped from the block by the next registry write.
- Slots: the manifest's `slots` field is documentation only; the bundle binds slots with `window.__HERMES_PLUGINS__.registerSlot(plugin, slot, Component)`. Only slots the shell actually renders are worth registering: `sessions:top` / `sessions:bottom` (inside SessionsPage) and the shell-wide `backdrop` / `header-left` / `header-right` / `header-banner` / `pre-main` / `post-main` / `overlay`. The documented `sidebar` slot is NOT rendered by this build of the shell (no cockpit rail; `layoutVariant` is carried as a data attribute nothing consumes), so registering it would be dead code. A slot component takes no props and must degrade to nothing on failure (it renders on a host page the plugin does not own).

## Layout

- `plugin.yaml` - manifest; plugin id `topoi`, platform name `topoi`.
- `adapter.py` - `TopoiAdapter` + `register()`; `__init__.py` re-exports `register`.
- `topic_store.py` - the topic registry (the `platforms.topoi.topics` config block): normalize/validate a stored or client-sent state (only `entries` / `updated_at` are read; the retired `items` / `revision` spellings are ignored and logged once), read it through the core's config cache, write it last-writer-wins under the core's config lock, mirror a moved home topic onto the framework's `home_channel`, repair that projection at connect when it is missing or stale (`repair_home_projection`), and surface a legacy config-level `bindings` block for one-time adoption. The adapter and the REST layer both read it live, which is why a home change needs no restart.
- `bindings.py` - the session-to-topic index: a plugin-private SQLite store (`<hermes home>/plugin-data/topoi/bindings.db`, WAL, per-operation connections) keyed by lineage root. Bindings are high-churn and unbounded, which is why they are not in config; the REST layer resolves them server-side so clients never see the map. Prunes against the live registry entries, sweeps roots whose session is gone (past a threshold, on write paths), and adopts a legacy config block once.
- `dashboard/plugin_api.py` - the REST surface (`GET`/`PUT /topics`, `GET /threads`, `POST /threads/bind`, `DELETE /threads/{session_id}`), mounted under `/api/plugins/topoi/`. Loaded BY PATH by the web server (module name `hermes_dashboard_plugin_topoi`), not as a package module, so it cannot use relative imports and loads its sibling modules (`topic_store`, `bindings`) itself with a path-load fallback. `GET /threads` resolves a row's topic through three legs in order: an adapter-minted `chat_id` (`source: topoi`), the binding store, then - for a scheduled run (`source: cron`, `cron_<job id>_<stamp>`) - the job's own delivery lane read from the profile's `cron/jobs.json` (`topoi:<topic>`, a bare `topoi` being the home topic, `failure_deliver` as the fallback), which is what makes a briefing the SAME session under its topic and under the Cron platform listing. That lane read happens only when the listing actually carries a run, is never cached, and nothing is written for it. The bind endpoint's logic lives in the sync `_bind_core` function (validation, lineage walk, store write, sweep); the async handler is a thin wrapper that owns the request parsing and the db lifecycle and maps `LookupError` to 404, `ValueError` to 422 and `BindConflict` to 409, which is what makes the write path drivable from a plain sync check. A plain bind never re-topics an existing filing: `_bind_core` reads the root's current binding and refuses a different topic unless the body says `move: true` (the row menu's Move to topic), so a stale new-thread arm that catches an already-filed chat - including one whose id rotated under compression - cannot relocate the thread. The delete route delegates the row, its compression chain and its on-disk artifacts to the core's own session delete handler (chain-aware, 409 under an active turn, already-absent is a no-op) and drops the thread's binding around it.
- `dashboard/manifest.json` - the dashboard extension manifest: `name` (must equal the plugin id and the bundle's `register()` name), `label` ("Topics"), `icon` (a Lucide name from the host's `ICON_MAP`, unknown names fall back to Puzzle), `version`, `tab.path` (`/topics`), `tab.position` (`after:sessions`), `slots` (documentation only; the real binding is `registerSlot()` in the bundle), `entry` (`dist/index.js`), `api` (`plugin_api.py`). The host renders plugin tabs in a separate "Plugins" sidebar section at the end of the nav, so the position hint orders the tab among the plugin tabs (first, here) rather than literally after Sessions.
- `dashboard/dist/index.js` - the dashboard bundle: a plain IIFE over the host's plugin SDK with two registrations, `register("topoi", TopicsPage)` for the tab (registry CRUD) and `registerSlot("topoi", "sessions:top", TopicsSlotCard)` for the topic-overview card on the Sessions page. The `sidebar` slot is documented in the SDK but NOT rendered by this build of the shell (no cockpit rail exists, and nothing consumes `layoutVariant` beyond a data attribute), so it is deliberately not used. See the dashboard bundle rules under Conventions.
- `desktop/plugin.js` - the desktop half (the Hermes Desktop app): a topics pane whose thread rows carry the app's own session statuses, a topic tab, and plugin settings pages. Written against the Desktop Plugin SDK; the folder name must equal the plugin id.
- `CONTRACT.md` - the published contract: identifiers, configuration, REST surface, delivery contract, events, install shape. Canonical here; clients vendor a pinned copy.
- `tests/check_topic_store.py` - the registry store against a throwaway `HERMES_HOME`: the seeded home, the YAML round trip, unrelated sections surviving, the refusal set, the home mirror, tolerant reads of a hand-edited block, and the legacy-bindings-block lifecycle (ignored on read, surfaced for adoption, dropped by the next write).
- `tests/check_bindings.py` - the binding store against a throwaway `HERMES_HOME`: the store lifecycle (set, overwrite, clear, mapping, persistence across fresh connections), pruning against the live topic set, the dead-root sweep with its threshold, root-shape refusal, the one-time adoption of a legacy config block, the cross-module seams the REST write path composes (a registry write pruning the store; the live-topic check gating a bind), and the sync bind core the async handler wraps (validation order, response shape, store effect).
- `tests/check_adapter.py` - the adapter contract: the `edit_message` capability contract (must stay the base method so the runner keeps draining tool progress), delivery evidence without a listener, the continuable thread mint, the `deliver=topoi:<topic>[:<thread>]` target syntax, and the standalone sender.
- `tests/check_backend.py` - the REST read paths against a seeded state.db: the registry read (no bindings map), the live-topic-only listing with its compression-tip projection, topic resolution from `chat_id` and through the binding store, the cron-run legs (a `cron_<job id>_<stamp>` session filing under its job's delivery lane: explicit topic, bare home, dead topic, local-only, unknown job, comma-separated and list-shaped lanes, the failure lane, a thread suffix, a compressed run, and a client binding winning), the lineage walk the bind handler resolves roots with, and the delete route (row gone, binding dropped).
- `pyrightconfig.json` - editor/LSP import resolution (points at the hermes tree).

## Checks

- `~/.hermes/hermes-agent/venv/bin/python tests/check_topic_store.py`
- `~/.hermes/hermes-agent/venv/bin/python tests/check_bindings.py`
- `~/.hermes/hermes-agent/venv/bin/python tests/check_adapter.py`
- `~/.hermes/hermes-agent/venv/bin/python tests/check_backend.py`
- `hermes plugins doctor topoi` - validates discovery, manifest, import, registration.

Note: the checks need the hermes-agent tree on `sys.path`; they set `HERMES_HOME` to a throwaway directory themselves, so the real `config.yaml` is never touched. On an install whose tree venv is stale (`hermes update` owed), `hermes_bootstrap` relaunches every script on the managed runtime with `-I`, which drops the venv's site-packages and fails at `import yaml` / `import fastapi`; prefix `HERMES_DISABLE_LAZY_INSTALLS=1` to skip that relaunch and run under the venv as documented.

## Dev loop

- Repo lives in place at `~/.hermes/plugins/topoi` (the dir IS its git checkout); its GitHub remote is the publish target.
- Config: `hermes config set platforms.topoi.<key>` (never hand-edit `config.yaml`).
- Plugin code and `plugin.yaml` load once per gateway process: run `hermes gateway restart` to apply. There is no hot reload.
- The REST routes mount at web-server startup; a new or changed `plugin_api.py` needs a backend restart.
- Dashboard discovery is cached per dashboard process: a new or changed `manifest.json` / `dist/index.js` needs `hermes-dashboard.service` restarted (or `GET /api/dashboard/plugins/rescan`, which is behind the dashboard's auth gate). The entry bundle itself is served from the plugin directory per request, so only discovery needs the restart; the browser must reload to pick up the new manifest (manifests are also cached in sessionStorage per tab).
- Bundle syntax: `node --check dashboard/dist/index.js`. There is no build, lint or test step for the bundle; its behavior is verified against a live dashboard (a second dashboard on a throwaway `HERMES_HOME` plus headless chromium over CDP).
- The second dashboard for verification is launched exactly like `hermes-dashboard.service` does it: `set -a && . ~/.hermes/.env && set +a && HERMES_DISABLE_LAZY_INSTALLS=1 HERMES_HOME=<tmp> ~/.hermes/hermes-agent/venv/bin/python -m hermes_cli.main dashboard --port <free> --host 127.0.0.1 --no-open --skip-build`. Do NOT use the `hermes` launcher with a temp home: its venv-currency check is home-sensitive (the shared venv was synced for the real home's plugin extras), so the launcher re-runs `pm.sync_venv` against the shared environment (slow, mutating) or resolves the dep-less tools python (`ModuleNotFoundError: ruamel`).
